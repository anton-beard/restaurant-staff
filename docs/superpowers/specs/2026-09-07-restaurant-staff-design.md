# Обучение и контроль персонала ресторана: дизайн

Дата: 2026-09-07. Статус: согласован с владельцем проекта.

## 1. Цель и рамки

Система для одного ресторана с одним владельцем. Владелец через веб-админку заводит сотрудников, задания, курсы и тесты. Сотрудники работают только через Telegram-бота: получают задания, отчитываются фото, читают уроки, проходят тесты. Фото проверяет Claude, спорные случаи уходят владельцу.

В рамки входит:
- Админка владельца, вход по одноразовому коду из Telegram.
- Telegram-бот для сотрудников и владельца.
- Разовые и регулярные (по расписанию) задания, часть с фото-подтверждением.
- Автоматическая оценка фото Claude с гибридным решением: уверенное «хорошо» принимается автоматически, остальное на ручную проверку.
- Курсы (уроки + итоговый тест) по должностям и отдельные тесты по расписанию.
- Сводка с рейтингом сотрудников и уведомления владельцу в боте.

Не входит:
- Несколько ресторанов или владельцев, роли менеджеров.
- Telegram Mini App (может появиться позже поверх этой архитектуры).
- SMS, внешние БД, S3.

## 2. Стек и структура

- Node.js 24, TypeScript, один процесс.
- Fastify: REST API под `/api/`, статика админки, `/healthz`.
- grammY, long polling (публичный вебхук не нужен).
- SQLite через better-sqlite3, миграции простыми SQL-файлами с номерами.
- node-cron: планировщик внутри процесса, тик раз в минуту.
- Vue 3 + Vue Router + Tailwind, сборка Vite в статику.
- Валидация входа API и ответов Claude: zod.
- Тесты: Vitest. Клиент Telegram и Claude в тестах мокаются.
- Docker: multi-stage образ, docker-compose с volume `./data:/data`.

Папки:

```
server/            Fastify, бот, планировщик, БД, ИИ
  api/             роуты админки
  bot/             хендлеры grammY
  scheduler/       регулярные задания, напоминания, просрочки
  ai/photoReview.ts
  db/              подключение, миграции, запросы
admin/             Vue-приложение
data/              том: app.db, uploads/
docs/superpowers/  спеки и планы
```

Переменные окружения: `BOT_TOKEN`, `ANTHROPIC_API_KEY`, `OWNER_PHONE`, `SESSION_SECRET`, `DATA_DIR` (по умолчанию `/data`), `PORT`.

## 3. Модель данных

Все id целые автоинкрементные, даты в ISO-строках UTC.

- **positions**: id, name. Должности заводит владелец.
- **employees**: id, full_name, phone (E.164, уникальный), position_id, telegram_id (null до привязки, уникальный), status: `invited` | `active` | `archived`, created_at.
- **task_templates**: id, title, description, requires_photo, photo_criteria (текст критериев для ИИ), auto_accept_threshold (0..100, по умолчанию 80), schedule (null для разового; для регулярного cron-выражение в локальном времени ресторана), deadline_hours, assignee_mode: `by_position` | `by_employees`, active, created_at.
- **task_template_positions**: template_id, position_id.
- **task_template_employees**: template_id, employee_id.
- **task_instances**: id, template_id, employee_id, issued_at, due_at, status: `pending` | `submitted` | `review` | `accepted` | `rejected` | `overdue`, completed_at, reminder_sent_at. Уникальность (template_id, employee_id, issued_at по дате) защищает планировщик от дублей.
- **task_submissions**: id, instance_id, photo_path, telegram_file_unique_id (уникальный), ai_score, ai_verdict, ai_issues (json), ai_error (текст, если ИИ недоступен), decision: `auto_accepted` | `needs_review` | `owner_accepted` | `owner_rejected`, owner_comment, created_at, decided_at.
- **courses**: id, title, description, due_days, active. **course_positions**: course_id, position_id.
- **lessons**: id, course_id, order, title, body (markdown), media (json-список путей к картинкам и ссылок на видео).
- **quizzes**: id, title, course_id (null для отдельного теста), pass_score, schedule (cron или null), active. **quiz_positions**: quiz_id, position_id.
- **questions**: id, quiz_id, order, text, options (json-массив строк), correct_index.
- **course_progress**: id, employee_id, course_id, assigned_at, due_at, lessons_read (json-массив lesson_id), status: `in_progress` | `completed` | `overdue`. Уникальность (employee_id, course_id).
- **quiz_assignments**: id, employee_id, quiz_id, assigned_at, due_at, status: `pending` | `passed` | `failed` | `overdue`. Для тестов курса создаётся при завершении уроков, для тестов по расписанию планировщиком.
- **quiz_attempts**: id, assignment_id, answers (json), score, passed, created_at.
- **bot_states**: telegram_id, state (json). Текущий диалог: какой тест проходится, какое задание ждёт фото.
- **owner_login_codes**: id, code_hash, expires_at, used. **owner_sessions**: id, token_hash, expires_at.
- **settings**: key, value. Хранит owner_telegram_id.

Рейтинг не хранится, считается запросом за период: доля заданий, принятых в срок, и средний балл тестов.

## 4. Бот

Состояние диалога только в `bot_states`, перезапуск ничего не теряет.

**Привязка.** `/start` от неизвестного telegram_id показывает кнопку «Поделиться номером» (request_contact). Номер нормализуется до E.164. Совпал с `OWNER_PHONE`: telegram_id пишется в settings, владелец получает меню владельца. Совпал с employee в статусе `invited`: telegram_id сохраняется, статус `active`, владелец получает уведомление «сотрудник подключился». Не совпал: «Вас ещё не добавили, обратитесь к владельцу». Контакт принимается только если это контакт самого отправителя (user_id совпадает).

**Меню сотрудника** (reply-клавиатура): «Мои задания», «Обучение», «Тесты», «Мой рейтинг».

**Задания.** Список активных экземпляров с дедлайнами. Внутри: описание, кнопка «Выполнено». Без фото: инстанция сразу `accepted`. С фото: бот просит снимок, state запоминает instance_id. Полученное фото (только тип photo, не document) скачивается в `data/uploads/<instance_id>/<timestamp>.jpg`, создаётся submission, инстанция `submitted`, запускается проверка (раздел 5). После проверки сотрудник получает один из ответов: «Принято, N из 100», «Отправлено владельцу на проверку», а после решения владельца «Принято» или «Не принято: <комментарий>. Переснимите». Отклонённая инстанция возвращается в `pending`, дедлайн не меняется.

**Обучение.** Список назначенных курсов с прогрессом «3 из 7 уроков». Урок отправляется текстом (markdown переводится в HTML Telegram) с картинками, снизу кнопка «Прочитал, дальше». После последнего урока создаётся quiz_assignment итогового теста и предлагается пройти.

**Тесты.** Список ожидающих. Вопросы по одному, варианты инлайн-кнопками, state хранит номер вопроса и ответы. В конце балл и результат. Провал: можно пересдать сразу, попытки не ограничены. В отчётах показываются лучшая и последняя попытка.

**Мой рейтинг.** Доля заданий в срок и средний балл за 30 дней, место среди коллег.

**Уведомления сотруднику**: новое задание, новый курс, новый тест сразу при назначении; напоминание за 2 часа до дедлайна; сообщение о просрочке; решение владельца по фото.

**Меню владельца**: краткая сводка на сегодня и ссылка на админку. Уведомления владельцу: фото на ручную проверку (само фото, оценка ИИ, замечания, кнопки «Принять» и «Отклонить»; отклонение просит ввести комментарий следующим сообщением), просрочка задания, проваленный тест, подключение сотрудника.

## 5. Проверка фото через Claude

Модуль `server/ai/photoReview.ts`, одна функция `reviewPhoto(imageBuffer, criteria)` возвращает `{ score: number, verdict: string, issues: string[] }`.

- Модель `claude-sonnet-5`, фото как base64 image block, критерии в тексте. Промпт требует ответ строго JSON, ответ проверяется zod-схемой.
- Таймаут 30 секунд, один повтор через 3 секунды. После второй неудачи бросается ошибка.
- Решение: score ≥ `auto_accept_threshold` шаблона: submission `auto_accepted`, инстанция `accepted`, `completed_at` проставляется. Иначе, включая явно низкие баллы: submission `needs_review`, инстанция `review`, владельцу уведомление. Автоматических отклонений нет.
- Ошибка ИИ: submission `needs_review` с `ai_error`, владелец видит пометку «ИИ недоступен». Сотрудник видит «отправлено на проверку».
- Защита от подмены: `telegram_file_unique_id` уникален, повторная отправка того же фото отклоняется с просьбой снять заново.
- Тесты: мок клиента, разбор корректного JSON, невалидный JSON, таймаут, пороги 79/80.

## 6. Админка

**Вход.** Страница с кнопкой «Получить код». Сервер создаёт 6-значный код на 5 минут, хранит хеш, бот отправляет код владельцу на `owner_telegram_id`. Если владелец ещё не привязан, страница объясняет, что нужно написать боту. Ввод кода: 5 неверных попыток за 10 минут блокируют выдачу и проверку на 15 минут. Успех: httpOnly, SameSite=Lax cookie с токеном сессии на 30 дней. Все `/api/` ручки, кроме логина и `/healthz`, требуют сессии.

**Экраны:**
- Сводка: задания сегодня и за неделю (в срок / просрочено / на проверке), очередь фото, средний балл тестов, рейтинг сотрудников за выбранный период (7, 30, 90 дней), просрочки подсвечены.
- Сотрудники: таблица, добавление (имя, телефон, должность), редактирование, архивирование. Карточка: история заданий, курсов, тестов.
- Должности: справочник.
- Задания: шаблоны с формой (название, описание, фото требуется, критерии, порог, разовое или расписание, дедлайн в часах, исполнители по должности или поимённо). Разовый шаблон при сохранении сразу создаёт экземпляры. Список экземпляров с фильтрами по статусу, сотруднику, дате.
- Проверка фото: очередь `needs_review`, фото крупно, оценка и замечания ИИ, кнопки принять и отклонить с комментарием. Решение из админки и из бота эквивалентно.
- Обучение: курсы с уроками (markdown-редактор, загрузка картинок), назначение по должностям; тесты с вопросами, привязка к курсу или расписание.

Файлы: картинки уроков и фото заданий загружаются в `data/uploads`, отдаются через `/api/uploads/...` только за сессией. Разрешены только jpg, png, webp, до 10 МБ.

## 7. Планировщик

Тик раз в минуту, все шаги идемпотентны:
1. Для активных регулярных шаблонов, чей cron совпал с текущей минутой, создать экземпляры всем подходящим активным сотрудникам, если экземпляра на эту дату ещё нет. Отправить уведомления.
2. Для тестов с расписанием создать quiz_assignments так же.
3. Новым активным сотрудникам назначить курсы их должности, которых у них ещё нет (также при смене должности).
4. Напоминание за 2 часа до `due_at` для `pending`, где `reminder_sent_at` пуст.
5. Перевести в `overdue` инстанции `pending` и назначения с истёкшим `due_at`, уведомить сотрудника и владельца.

Cron-выражения интерпретируются в часовом поясе ресторана (`TZ` контейнера).

## 8. Ошибки и устойчивость

- Ошибки в хендлерах бота логируются, пользователю уходит «Что-то пошло не так, попробуйте ещё раз»; бот не падает.
- Ошибка отправки уведомления (сотрудник заблокировал бота) логируется и не блокирует остальные.
- Один процесс пишет в SQLite, WAL включён; планировщик и бот работают в одном event loop, конфликтов записи нет.
- Бэкап: копия папки `data`.

## 9. Тестирование

- Unit: нормализация телефона, расчёт рейтинга, логика решения по фото, разбор ответа Claude, идемпотентность планировщика (БД в памяти).
- API: Vitest + inject Fastify на in-memory SQLite: авторизация, CRUD, очередь проверки.
- Бот: хендлеры вызываются с поддельными update и моком API Telegram, проверяются состояние в БД и отправленные сообщения.
- Ручная проверка: тестовый бот и реальный ключ Claude на одном фото.

## 10. Этапы реализации

Каждый этап получает собственный план и заканчивается рабочим продуктом.

1. **Каркас**: проект, БД и миграции, Fastify с `/healthz`, бот с привязкой по номеру, вход владельца по коду, админка с сотрудниками и должностями, Docker.
2. **Задания**: шаблоны, экземпляры, разовые и регулярные, фото, проверка Claude, очередь ручной проверки, уведомления по заданиям.
3. **Обучение**: курсы, уроки, тесты, назначения, прохождение в боте, уведомления.
4. **Контроль**: сводка, рейтинг, карточка сотрудника, оставшиеся уведомления владельцу.
